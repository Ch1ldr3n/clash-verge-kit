## Spec

### P1：不同目标订阅可复用同一私有节点缓存

修复前位置：`src/routing-runtime.ts` 的私有别名生成。原先只对 `[sourceId, provider]` 哈希；两个目标的来源 ID 都是 `target`，同名 provider 会生成相同私有名称和缓存路径。目标身份与实际来源没有进入缓存身份。

对应要求：[规则分流 V1](../specs/2026-09-05-rule-routing-v1.md) 的来源/原名隔离、A4 和 A16；[保存合同](../specs/2026-09-05-routing-persistence-design.md) 要求保留旧修订的完整脚本识别。

复现步骤全部使用合成数据：

1. 由公开生成器分别为目标 A、B 生成脚本；两个目标都有名为 `pool` 的 provider，选中节点同名，但来源不同。
2. 在独立 Mihomo 中运行 A，成功取得 A 的私有 provider 缓存。
3. 切换到 B；B 自身有有效本机缓存，B 的 HTTP 来源返回 503。
4. 确认 B 配置已加载：普通 Native 组的真实请求返回 `SOURCE-B`。
5. Kit AI 手选组的真实请求却返回 `SOURCE-A`，因此“不得使用 A 的节点”断言失败。

本轮输出摘要：`pathsCollide=true`、`urlsDiffer=true`、`reloadAccepted=true`、`nativeObservedBody=SOURCE-B`、`observedBody=SOURCE-A`。不是仅凭名称相同推断，也不是配置未切换造成的误报。

可重复执行：

```powershell
node scripts/probe-routing-cache-isolation.mjs
```

修复前退出码 1 是确认缺陷的证据；修复后退出码 0，且明确断言缓存路径不同、B 首次失败时私有候选为空。探针不输出完整生成脚本或 YAML；退出时关闭自建内核和回环服务，并检查路径后删除自己的合成临时目录。原有 208 项回归与两组内核探针没有覆盖此场景。
